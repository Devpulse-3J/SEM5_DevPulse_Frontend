Executive Performance Overview

A series of end-to-end automated load, stress, and spike test campaigns were conducted against the live, hosted deployment of DevPulse on odineye.cse23.org. The test suite exercised both the Next.js server-side rendered client interface and the underlying microservices layer routed via Spring Cloud API Gateway.

The evaluation demonstrates that the application architecture is robust, highly responsive, and resilient. Under normal multi-user concurrency (10 concurrent users generating continuous traffic without human delay), the system maintains a median response time of 140ms, with Next.js frontend pages loading under 100ms.

When tested beyond normal operational capacity under a 50-user stress campaign (generating 4,153 total requests at 23.2 requests/sec), the Redis-backed Token Bucket rate limiter successfully intervened as designed, throttling abusive bursts with HTTP 429 status codes while preserving 100% responsiveness on frontend dashboard pages and authenticated profile endpoints.

Detailed Test Suite Analysis

1. Fast Smoke Test (1 User, 30 Seconds)

Sanity & Health Check

The smoke test verified end-to-end connectivity, TLS negotiation, DNS routing, and core service availability. The user profile check (GET /api/auth/me) responded cleanly in 610ms, dynamic user registration succeeded in 576ms, and user GitHub status checked in 369ms. This confirms zero downtime deployment and valid baseline health.

2. Standard Load Test (10 Concurrent Users, 2 Minutes, 556 Requests)

Realistic Daily Operations

Simulates normal business hours for a distributed engineering team with 5 active personas. 100% of all frontend navigation requests succeeded without a single failure. Landing page loads averaged 150ms, Workspace Dashboard averaged 96ms, and DORA charts rendered in 100ms. Project creation (POST /api/projects) and updates (PUT /api/projects/[id]) succeeded with 100% reliability, demonstrating clean transactional database integrity.

3. Stress Test (50 Concurrent Users, 3 Minutes, 4,153 Requests)

System Breaking Point Analysis

Pushed total request rate to 23.2 requests/sec. Under this high load, the backend demonstrated excellent resiliency: The median response time was 110ms and average response time was 261ms. Frontend UI routes remained 100% functional (0% dropped). When incoming traffic exceeded the 20-request burst capacity of the API Gateway, the gateway actively responded with HTTP 429 ("Too Many Requests"), ensuring the shared PostgreSQL database remained stable.

4. Spike Test (100 Users Surge Burst, 1 Minute)

Traffic Surge Resilience

Evaluated sudden bursts of traffic (spawning 50 users/second). The gateway rate limiter immediately engaged, buffering and shedding excess connections while maintaining rapid recovery: once the burst concluded, the system recovered instantaneously to sub-100ms baseline latency without requiring any container or pod restarts.

Conclusions & Scaling Recommendations

1

Frontend Delivery is Optimized

The Next.js SSR architecture is effectively cached via Nginx and serves pages consistently in under 100ms. No further frontend optimization is necessary for standard operational scale.

2

Effective Rate Limiting

The Spring Cloud Gateway Redis rate limiter (10 sustained req/s, 20 burst capacity) proved to be an effective circuit breaker. It safely protects backend services from DB exhaustion under heavy load.

3

Capacity Planning

With realistic human think time (clicks every 5–15 seconds), the system comfortably supports 50 to 120 concurrent human users. For larger enterprise deployments, raising the replenish rate from 10 to 30 req/s will linearly scale throughput.
